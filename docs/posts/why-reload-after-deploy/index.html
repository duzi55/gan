为什么进页面要再刷新一次——静态站缓存的门道

修完 bug 上线了，浏览器里却还是旧版，非要手动 reload 一次——顺着这个疑点，把 GitHub Pages 的三层缓存与部署竞态拆开看个明白

#架构#Web

起因

刚修完老内核浏览器的预取报错，刷新验证时却发现：明明说修好了，进页面还是老样子，非得再手动刷新一次才看到新版——怎么进个页面还要 reload 一次？这个问题值得单独写一篇——因为它不是 bug，是静态站缓存的正常运作，但没人讲透的话，它看起来就像 bug。

探讨：一次访问要穿过三层缓存

「我推上去了」和「访问者看到了」之间，隔着一整条链路：

本地构建 → bot 提交 docs → Pages 构建（1~2 分钟）→ Fastly CDN → 浏览器缓存

我拿线上站点实测了响应头（HTML 和 JS 资源各查一次）：

Cache-Control: max-age=600
Via: 1.1 varnish
X-Served-By: cache-hkg17922-HKG
Last-Modified: Fri, 28 Aug 2026 01:34:35 GMT

三个关键事实：

  1. GitHub Pages 所有文件统一 max-age=600——它不支持自定义响应头，HTML 和 JS 一视同仁，都是 10 分钟。GitHub Pages 背后是 Fastly CDN（X-Served-By 的 cache-hkg 就是香港边缘节点），CDN 自己也会缓存这份副本最多 10 分钟；
  2. polyfill 是修在 HTML 里的。老内核浏览器的那个预取报错，补丁位于根布局的 <head>，随 HTML 下发。访问者浏览器里还揣着上一版缓存的 HTML——里面没有补丁，报错自然「还在」。不是修复无效，是访问者拿的还是旧地图；
  3. Last-Modified 就是最新部署的时刻。对着它看就能知道当前缓存是新是旧。

所以「进页面要 reload 一次」的完整解释是：部署完成 ≠ 缓存过期。浏览器里那份旧 HTML 在 10 分钟有效期内会一直被优先使用，直到过期、或访问者强制刷新。

探讨：比「看到旧版」更凶的是部署竞态

还有个隐藏剧情：为什么有时候不刷新还好，一刷新反而白屏？

新版构建会给 JS 资源换内容哈希（本次部署构建清单就从 lVwiPJm… 换成了 5EcpcD8…），旧哈希的文件在新构建里不存在了。如果访问者浏览器里还揣着旧 HTML，页面会去请求已被删除的旧 chunk——404，页面直接崩掉。访问者拿着旧地图找已拆迁的房子，这是静态托管的经典「部署竞态」。刷新一次拿到新 HTML、新文件名，一切正常。

业界标准解法是「HTML 短缓存 + 资源内容寻址长缓存」：HTML 十分钟必过期，带哈希的资源随便缓存一年因为内容永不变化。GitHub Pages 用统一 10 分钟简化了这件事——代价是资源也只缓存 10 分钟，收益是竞态窗口同样只有 10 分钟。

方案：验证流程的三招

  1. 硬刷新（Ctrl+Shift+R）：绕过一切缓存直取最新，验收修复时用它，别用普通刷新（普通刷新仍会带着缓存里的子资源）；
  2. 无痕窗口：全新缓存视角，等效于「一个刚听说本站的访客第一次访问」；
  3. 查源码确认：view-source: 打开页面搜补丁关键字（比如这次搜 asyncIterator），在 HTML 里能看到 = 新版已到达这条线路，剩下的只是浏览器本地缓存没过期。

站点侧我没有做额外处理——Service Worker 灰度、保留旧版 chunk 这类方案对个人博客属于过度设计，10 分钟的窗口完全可以接受， architecture 上维持「内容寻址 + 短 HTML 缓存」的业界默认即可。

避坑

  • 「修复没生效」先过缓存关，再怀疑代码。三层各自过期时间不同：Pages 构建排队 1~2 分钟、CDN 最多 10 分钟、浏览器本地最多 10 分钟。逐层排除，别在旧缓存上调试新代码；
  • 可引用的验证条目：验证线上行为时，先 curl -I 看 Last-Modified 和 Cache-Control，确认拿到的是哪个版本的部署，再下「修复无效」的结论；
  • 静态托管的部署不是原子切换，是「新旧文件在 10 分钟窗口内共存」的渐进过程，任何依赖「立即全站生效」的假设都不成立；
  • 给协作者的沟通模板：改完版告诉对方「硬刷新一次」，比解释十条缓存原理管用。

一次 reload 引出一整条缓存链路。反馈无小事——每一次「怎么又要刷新」背后，都藏着一课。
