写博客总归是想配几张图的。于是问题来了：图放哪儿？

很多人第一反应是「找个免费图床」，或者干脆「单独建一个仓库存图，博客里远程引用」。我起初也这么想，推演了一圈之后发现——对这套 GitHub Pages 博客来说，**图片和文章坐在同一条船上，才是最快的路**。

## 为什么另开一个仓库反而更慢

这个站的所有内容都通过 `github.io` 分发，背后是 Fastly 的全球 CDN。如果图片放到别的仓库去，会遭遇两件事：

1. **raw 直链行不通**。`raw.githubusercontent.com` 在国内的连通状况比 `github.io` 还要糟糕，部分地区直接解析失败；而且它返回的是 `text/plain` 头，某些环境下浏览器不是显示图片而是触发下载。
2. **CDN 中转看运气**。jsDelivr 这类免费前端确实是经典方案，但这几年大陆节点的连通率时好时坏，哪天整段抽风，图文就分家了。

而图片放进博客自己的仓库，跟随站点一起发布、一起被 CDN 缓存：同域名意味着**不多付一次 DNS 解析和 TLS 握手**，页面里那张图和标题文字来自同一个地方。

## 本站的配图规范

所有配图统一存放在 `public/images/posts/` 目录：

```text
public/
└── images/
    └── posts/          ← 文章配图统一在这里
        └── ink-mountain-demo.jpg
```

在 Markdown 里引用时带上站点前缀 `/gan` 即可：

```markdown
![远山如黛](/gan/images/posts/ink-mountain-demo.jpg)
```

下面这张「远山如黛」就是按此规范入库的真实图片，它的加载速度就是你的读者将来看到的速度：

![远山如黛：水墨层峦，雾气留白](/gan/images/posts/ink-mountain-demo.jpg)

顺带的好处：

- **永不断链**——图床跑路是老一代博主最大的痛，图在自己仓库里就没有这回事；
- **版本可回溯**——改图也走 git commit，历史随时翻；
- **本地开发可见**——写文章时图片在本地预览就直接显示，不用联网到第三方。

## 瘦身三板斧

图放对了地方，还要让它足够轻。三个动作，效果立竿见影：

| 手段 | 说明 | 收益 |
| --- | --- | --- |
| 转 WebP | 有损压缩下体积通常再减三至五成 | 显著 |
| 压到显示尺寸 | 页面内容宽约 800px，就别塞四千像素的原图 | 显著 |
| 懒加载 | 首屏之外的图滚动到才加载 | 体感 |

第三条对应的写法是在图片标签上加 `loading="lazy"` 属性（用 HTML 写法替代纯 Markdown 语法）：

```html
<img src="/gan/images/posts/ink-mountain-demo.jpg"
     alt="远山如黛" loading="lazy" />
```

## 结语

配图的答案其实很朴素：**和网站待在一起，然后把自己变得很轻**。不需要注册图床账号，不需要研究外链防盗链，一个目录一把 commit 全解决。
