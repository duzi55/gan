## 最终架构

上一篇推演到了结论，这一篇把图纸摊开。整条链路只有四个角色：

```
任何设备浏览器
   │ 打开 /admin，点「GitHub 登录」
   ↓
GitHub 授权页 ──点授权──→ Cloudflare Worker（交换密钥）
   ↑                          │ 换得令牌，回传浏览器
   │ 写文章，点保存            ↓
   │                     浏览器直调 GitHub API 提交 commit
   │                          │ push 到 main
   └── 线上更新 ←── Actions 自动构建 ←──
```

日常写文章的动作被压缩到三个：打开后台，写，保存。其余全部自动。

## 为什么是 OAuth 加 Worker

OAuth 授权分两步：浏览器跳转 GitHub 拿到授权码，再用授权码加应用密钥换取真正的令牌。卡点在第二步——GitHub 不支持免密钥的交换方式，而密钥绝不能放进前端。

于是需要一个"保管密钥的手"。Cloudflare Worker 是全球 CDN 公司 Cloudflare 提供的边缘函数服务：代码部署到全球节点，有请求就近运行，平时不存在。免费档每天十万次调用，而登录后台这个动作一天用不到十次。

它只在授权的那几秒工作：收下 GitHub 带回的授权码，出示密钥换回令牌，把令牌还给浏览器。仅此而已。

## 安全设计四原则

这套网关虽小，该有的防线一道不少：

1. **密钥不落前端**——client_secret 只存 Worker 的加密环境变量，页面代码里永远不出现
2. **state 一次性**——发起授权时生成随机数存入 KV，十分钟过期、用后即焚，防跨站伪造
3. **令牌走暗道**——通过 URL 的 fragment（井号之后）回传，这部分不会进入服务器日志与浏览记录
4. **回跳白名单**——Worker 只把令牌送回预先登记的博客域名，防开放重定向

另外有一样东西天然安全：访客即使打开后台、走完授权，拿到的是他自己账号的令牌——他无权写我的仓库，等于拿着自己家的钥匙站在别人门口。

## Worker 部署六步

全程网页点击，无需命令行，约十分钟：

| 步骤 | 在哪 | 做什么 |
|---|---|---|
| 一 | GitHub → Developer settings | 创建 OAuth App，拿到两个密钥 |
| 二 | dash.cloudflare.com | 邮箱注册，免费计划 |
| 三 | Workers & Pages → Create | 建一个 Worker，粘贴网关源码 |
| 四 | Worker → Settings | 配三个变量、绑一个 KV |
| 五 | 回到 GitHub OAuth App | 回调地址填 Worker 真实网址 |
| 六 | 浏览器 | 访问 Worker 的 /auth 验收 |

完整的逐步图文（含界面位置与源码）存于仓库 `guides/cloudflare-worker-oauth.md`。

## 还差两块拼图

架构里另有两个角色，各司其职：

**/admin 编辑页**——博客里的一个静态页面。承担登录态管理、文章列表、markdown 编辑器、保存即提交。它是后台的"脸面"，本身也是纯前端，随博客一起构建发布。

**Actions 构建剧本**——仓库里的一个 yml 文件。监听 content 目录变更，自动构建并把产物提交回 main 分支。用 `[skip ci]` 标记防止构建触发构建的死循环，用 rebase 化解本地与云端同时推送的冲突。

## 写在最后

这篇博客本身，就是这套后台的第一个用例——它由 markdown 写成，走的是同一条「提交即上线」的流水线。将来某一篇在手机上、在旅途中、在别人电脑的浏览器里诞生的文章，也会沿着这条路回家。

静态站没有后端，但可以有后台。约束没有消失，只是被一一找到了出口。
